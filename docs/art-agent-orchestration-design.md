# 外接绘图 Agent：编排层设计与提示词契约（商定版 · 供升级参考）

> 给 maimai-drawpic-plugin 维护者的设计说明。
>
> 我们在本仓库之上做过一个**角色绘图编排插件**（下称「编排层」）：它不负责出图，
> 只负责把一句自然语言请求变成「抓哪些参考图 + 写什么提示词 + 每张图用在哪里」，
> 再交给本仓库的引擎出图。跑了若干版本、修过若干线上问题后，把其中
> **与具体角色无关的通用经验**连同中性化的参考源码一起整理进本 PR。
>
> 本 PR **只新增 `docs/` 一篇设计说明 + `references/` 下的参考源码**，
> 不改本仓库任何运行时代码、配置、界面与依赖；参考源码放在 `references/`，不进 `src/`。

---

## 0. 与维护者商定后的结论（本版取代初稿）

初稿建议「把编排层的通用经验按需吸收进本仓库」，并按「免费插画 / 付费图生图」
划分四条通道。双方讨论后改为以下结论，**本版文档以本节为准**：

| 议题 | 结论 |
|---|---|
| **基座** | **在本仓库（绘画插件）基础上升级**，不另起一个独立插件仓。编排能力作为本仓库的一层，复用现有引擎、配置与 WebUI |
| **目标形态** | 做成**外接绘图 Agent**：宿主 planner 只发一条指令，插件**内置的 LLM** 自行判断「要抓什么图、写什么提示词、哪张参考图用在哪里」 |
| **保留的能力** | ① 自带主人物多参考图 ② 场景预设 ③ 联网搜索参考图 ④ 聊天中抓取参考图 |
| **通道设计** | **不保留「免费 / 付费」多模型通道分流**。按成本选引擎是特定部署的个性化约束，不宜成为通用架构的分层依据；统一走本仓库的引擎与出图接口 |
| **UI** | 维护者已确认 **UI 不构成阻碍**，沿用本仓库现有 WebUI 体系；本方案不新增自定义页面，也不搬编排层那套控制台 |
| **参考源码** | 随 PR 附中性化后的核心源码，供逐行对照与重写；定位是**参考实现，不是可直接合入的补丁** |

> 说明：编排层原有的四通道命名（`self` / `cast` / `reference` / `illustration`）里，
> 曾按引擎计费差异把请求分到不同出图接口。那是为控制单次出图成本做的分流，
> **属于特定部署的成本管理，不是绘图请求本身的语义**。
> 商定后去掉这层分流：判路不再回答「用哪个引擎 / 花多少钱」，只回答
> 「画面里需要哪些素材、各自从哪来、派什么用场」。

## 1. 目标形态：一个会自己决定「怎么画」的外接 Agent

### 1.1 调用链

```
宿主 planner
    │  只发一条自然语言指令（不写提示词、不挑图、不选引擎）
    ▼
编排 Agent（本仓库升级后的一层，内置 LLM）
    │  读指令 + 会话上下文 + 可用图源
    │  输出一份结构化「绘制方案」
    ▼
本仓库统一出图接口（单一引擎 / 单一调用路径）
    ▼
图片 → 回传给宿主
```

关键点：**planner 与出图引擎之间不再由规则代码硬拼 prompt**，中间放一个
有决策能力的 LLM。planner 不必知道有哪些图库、怎么搜图、提示词该怎么写；
这些知识收进 Agent 自带的提示词（调用契约）里。

### 1.2 内置 LLM 的三项决策

| 决策 | 内容 | 为什么交给 LLM |
|---|---|---|
| **抓什么图** | 从 ① 主人物多参考图 ② 场景预设 ③ 联网搜索 ④ 聊天上下文 中挑出本次需要的素材 | 图源选择依赖语义（「照这张图画我」和「换个背景」完全不同），规则清单覆盖不全 |
| **写什么提示词** | 生成最终交给画面模型的那一段 `prompt` | 动作 / 表情 / 互动 / 构图应随情境变化，硬兜底会写出千篇一律的画面 |
| **哪张图用在哪里** | 明确每张参考图的**用途**：身份基准 / 造型 / 场景光线 / 构图 / 同伴 / 待改原图 | 同一张图在不同请求里用途不同；搞错用途是最常见的「画错人」根因 |

建议让 LLM 输出结构化结果再映射成接口参数，而不是直接吐一段自由文本：

```json
{
  "prompt": "…正面描述，只写画面里该有什么…",
  "references": [
    {"ref_id": "builtin/primary/01", "role": "identity",     "note": "主人物身份基准"},
    {"ref_id": "builtin/outfit/02",  "role": "outfit",       "note": "本次造型"},
    {"ref_id": "chat/<hash>",        "role": "scene",        "note": "只取场景与光线"},
    {"ref_id": "web/<id>",           "role": "composition",  "note": "构图参考"}
  ],
  "notes": "用户明确指定的衣服优先于预设"
}
```

`role` 建议固定成有限枚举（`identity` / `outfit` / `scene` / `composition` /
`companion` / `edit_target`），方便下游按用途决定**喂给哪一路、要不要压过其它图**。
编排层踩过的坑：会话里那张「人物设定稿」应判成该角色的形象参考并**压过**
搜来的泛化图；纯场景图则只取场景 / 光线 / 构图，不能当身份基准。

### 1.3 为什么不做硬清单

使用者明确偏好 **开放式引导 > 规则清单**：把「该有什么动作、什么表情、
怎么互动」写死成 N 条兜底规则，产出的画面会僵且规则永远补不全。
正确做法是在 Agent 自带的提示词里写**调用契约**（有哪些图源、有哪些 role、
输出什么结构、什么必须交给模型判断），把内容判断留给模型。
只有「模型不可能知道的机制事实」才写硬规则（例如图片段只有 hash 无 base64）。

## 2. 商定保留的四项能力

### 2.1 自带主人物多参考图

内置一组主人物参考图，**多张、可分组（身份 / 造型 / 角度）、可指定主形象**。
身份一致性靠**喂图**承载，不靠在 prompt 里反复重述外貌（见 §4.2）。
典型用法：同一套衣服的多张图按同一套画；用户当场点名换装时按用户说的来。

### 2.2 场景预设

把常用场景 / 光线 / 构图存成预设，请求命中时取对应预设图而非每次重新搜。
预设与联网搜图是**并列图源**，由内置 LLM 判断本次用哪个、或都用。

### 2.3 联网搜索参考图

按角色名 / 场景关键词检索候选图 → 打分过滤 → 取前 N 张。
两条纪律：**候选要先审再用**（避免把无关图当身份基准）；**搜不到就明说缺谁并请用户补图**，
不要硬画一个凭空捏的人。参考实现里 `min_score` / `max_candidates` / 审核模型都可配。

### 2.4 聊天中抓取参考图 —— 最容易踩坑、最通用

**问题**：聊天里引用 / 附带的图片，在 MaiBot 消息段里往往**只有 hash、没有 base64**。
直接 `get_by_id` 结构上取不到原图，导致「用户明明发了参考图，却判成无图」。
这一条前后改坏过四个版本才定位到。

**方案（三级回退）**：

1. 段内 `base64`（同一条消息直接带的图片）；
2. 从 `mai_messages.raw_content`（msgpack）取图片段；
3. 按 hash 从 `data/images/<hash>.{jpeg,jpg,png,webp,gif}` 读盘。

约束：`get_by_id` 抛异常**不许提前 return**；取不到由工具判断，只有工具明确说
「没有可用参考图」才请用户补图，**不能凭上一轮印象拒绝出图**。
另需跳过「自己刚发的成品图」，否则重画时会越改越偏。

→ 这一条对「需要先拿到历史图片再出图」的场景都通用，建议优先吸收进
`infrastructure/media/`（本仓库已有 `downloads.py` 负责逐跳校验 HTTP(S) 下载）。

## 3. 内置 LLM 的提示词分层（L1 / L2 / L3）

| 层 | 谁在读 | 写什么 |
|---|---|---|
| **L1 判路** | 轻量模型（utils 链） | 输出结构化 JSON：涉及哪些角色、需要哪些图源、是否带图 |
| **L2 调用契约** | 宿主 planner / Agent 自带提示词 | tool 的 `brief_description` / `detailed_description`：有哪些图源、role 枚举、输出结构、必须由模型判断的事 |
| **L3 画面内容** | 扩散 / 绘图模型 | **只有一个 `prompt` 字符串**，无 system role、无 `negative_prompt`、无多轮对话 |

**关键纪律**：**Agent 自带的提示词写 L2 调用契约，不要把一长串
「资深插画师请遵守 N 条规则」塞给 L3 画面模型**——那等于把否定词喂给画面模型，
触发 §4.2 的反噬。身份一致性靠参考图承载，不靠文字里反复重述。

## 4. 值得吸收的通用工程经验（按价值排序）

### 4.1 单 `prompt` 画面模型的提示词纪律 —— 最反直觉

**问题**：Seedream 这类**只有一个 `prompt` 字段、不是 LLM** 的模型，
**会把被否定的名词当成画面元素**。早期版本在 `avoid` 里写
「不要立体鸟形头饰」「不要整只眼睛发紫」「避免活鸟」，结果画面真的出现了
立体鸟形发夹、整只眼睛发紫、以及一只额外的鸟。

**方案（纪律，不是代码）**：

- 负面词清单**清空**；身份特征只写正面描述（发饰只提一次，并明确写「是发饰」）。
- 用一句 `scene_hint` **开放式引导**，让 LLM 自己判断该有的动作 / 表情 / 互动。
- 最终 prompt **落盘快照 + lint**：统计身份名词与否定词出现次数，超阈值告警。
  据此发现改版前最终 prompt 里身份名词 7 次、否定词 23 次；减到 2 / 14 次后该类瑕疵消失。

**核心红线：绝不要往 prompt 里写「不要画 XX」这类否定句。**
真正的正负分流需要引擎支持独立 `negative_prompt`，属于换引擎的问题。

### 4.2 任务可靠性：提交边界 / 幂等 / 失败回退

商定后虽不再按费用分流，但**任务可靠性纪律仍然适用**：

- **只读预检放在抓图之前**（避免白搜一轮图又被拒）；
- **45 秒同句幂等**：同会话 + 同句只放一次，且**只在提交成功后记账**（治「有疑问就反复发起绘图」）；
- **出图失败发一句人话通知 + 退回本次占用**（失败不能静默、不能白扣）。

→ 可吸收进本仓库 `application/` 已有的额度 / 任务服务，作为通用任务语义。

### 4.3 带图请求的判路模式

带图时若画面里其实有主人物本人，要补上身份基准图，
否则本人会被画成一个无关路人。判路本身与角色相关，但
**「带图时先让判别模型判断图与角色的关系，再决定图派什么用场」**这个模式通用；
另外，**降级不能降错方向**：缺图时应先问判别模型，而不是一律降到「纯插画」。

## 5. 明确不做 / 不搬的部分

| 不做 | 理由 |
|---|---|
| **免费 / 付费多模型通道分流** | §0 商定结论：成本是特定部署的个性化约束，不做通用架构分层 |
| 自定义 WebUI / 控制台 | 维护者已确认 UI 不构成阻碍，沿用本仓库 WebUI 与 `build_webui.py` 流水线 |
| 角色专属外貌描述 | 这是**配置不是逻辑**，参考源码里已占位，应由使用者自行填写 |
| 单文件约 3.8K 行 `plugin.py` | 本仓库是四层结构，应**按设计重写而非拷贝** |
| VLM 迭代闭环（生图 → 看图打分 → 再修） | 成本与延迟各 ×2–3，群聊场景等不起 |
| vendor 绘图客户端副本 | 本仓库自身已有等价实现，回灌只会造成目录与版权归属混乱 |

| 文件 | 内容 |

与 §0 商定后的目标形态并不一致。请把它当作
「三级取图 / 用途判定 / 提示词契约 / 可靠性纪律」的**逐行参考**，
按本仓库四层结构重写，不要原样合入。

## 8. 建议落地步骤（供维护者评估）

1. **先沉淀最小通用模块**：三级取图（§2.4）+ 单 `prompt` 提示词纪律（§4.1）。
   收益最大、风险最低、不碰核心。
2. **再定内置 LLM 的决策契约**（§1.2）：先把 `role` 枚举与结构化输出定下来，
   图源逐个接入（主人物多参考图 → 场景预设 → 联网搜图 → 聊天抓图）。
3. **然后增强任务服务**：提交边界记账、幂等、失败通知与回退（§4.2）。
4. **全程不引入免费 / 付费通道分流**，统一走本仓库出图接口。
5. **每步遵循本仓库 `AGENTS.md`**：改配置升 `config_version`、新增字段同步
   `localization.py`（en / ja / ko + zh-CN 默认）、提交前 `git diff --check` + 测试、
   WebUI 改动走 `build_webui.py`、不提交 `config.toml` / 密钥 / 日志 / 截图。
